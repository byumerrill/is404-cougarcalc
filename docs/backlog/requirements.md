# Release 2 Requirements (release-02-postgresql)

## Overview

You are preparing CougarCalc for **Release 2**.

Release 1 deployed CougarCalc as a Node.js/Express application running as a Linux service.

Release 2 introduces a new business requirement:

> Users want their calculation history to persist between application restarts and remain separate from the history of other anonymous browser clients.

For this release, "user-specific" means **browser-specific**, not a verified human identity. A browser profile is recognized by an opaque server-generated cookie. Different browsers, browser profiles, and devices have different histories. Clearing the cookie starts a new history identity.

The deployment model does **not** change.

The application will continue to run directly on Ubuntu as a Node.js application. PostgreSQL will be installed separately as its own Linux service.

Do **not** introduce Docker, containers, reverse proxies, cloud services, authentication systems, ORMs, or unnecessary architectural complexity. Those belong to later releases.

---

# Primary Goals

Implement persistent calculation history while preserving the simplicity of the existing application.

Prevent one anonymous browser client from receiving another anonymous browser client's calculation history without collecting IP addresses or introducing user accounts.

The resulting application should be suitable for tagging as:

```
release-02-postgresql
```

---

# Functional Requirements

## FR-1 Persist calculations

Every successful calculation shall be saved in PostgreSQL.

Each history record shall include at least:

- unique identifier
- timestamp
- arithmetic expression
- calculated result
- an association with the anonymous browser client that submitted it

Choose appropriate PostgreSQL data types.

---

## FR-2 Retrieve history

Implement:

```
GET /history
```

This endpoint shall:

- return only the current anonymous browser client's calculation history as JSON
- return the newest calculations first
- return HTTP 200 on success
- return an empty array when that browser has no calculations

It shall never return records associated with another browser identifier.

---

## FR-3 Update calculation endpoint

The existing endpoint:

```
POST /calculate
```

shall continue to:

- accept a calculation request
- perform the calculation
- return the calculated result

Additionally, before returning a successful response, it shall save the calculation to PostgreSQL.

The saved row shall be associated with the anonymous browser identity established for the request.

Its existing behavior and response format should remain unchanged whenever possible.

---

## FR-4 Preserve existing behavior

Existing calculator functionality must continue working exactly as before.

Do not modify existing functionality except where required to support persistent history.

# Anonymous Browser History Requirements

## ABH-1 Server-generated opaque identifier

When a request does not contain a valid CougarCalc history cookie, the server shall generate a cryptographically strong, unguessable random token and return it in a cookie.

The identifier shall:

- be generated by the server using a cryptographically secure random source;
- contain at least 256 bits of randomness;
- not contain or be derived from an IP address, user-agent fingerprint, hostname, email address, student identifier, or other personal identifier; and
- never be accepted from a request body, URL, or query-string parameter.

## ABH-2 Cookie security

The history cookie shall be:

- `HttpOnly`;
- `SameSite=Lax` or stricter;
- scoped to `Path=/`;
- persistent across normal browser restarts for a documented duration; and
- marked `Secure` whenever the application is running in a production HTTPS environment.

Use an optional `HISTORY_COOKIE_SECURE` environment variable with a strict `true` or `false` value to control the `Secure` attribute. It may default to `false` for local and course HTTP environments, and it must be set to `true` for an HTTPS deployment. Local HTTP development must remain usable without weakening the configured production behavior.

Missing, malformed, or unreasonably large cookie values shall be replaced with a newly generated identity rather than causing an application error.

## ABH-3 Protect the identifier at rest

The raw cookie token is a bearer secret. PostgreSQL shall store only a deterministic cryptographic hash of the token, never the raw token.

The raw token shall appear only in the browser's `Cookie` request header and the server's required `Set-Cookie` response header. Neither the raw token nor its hash shall be written to response bodies, HTML, application logs, error messages, or committed configuration files.

## ABH-4 Browser-scoped persistence

Both calculation insertion and history retrieval shall be scoped by the hash of the current browser token.

- The same browser profile and cookie shall see its history after page refreshes, browser restarts, and Node.js application restarts.
- Different browsers, profiles, or devices shall not see one another's history.
- Clearing or replacing the cookie shall create a new anonymous history identity.
- Anonymous history is not expected to follow a person to another browser or device.

## ABH-5 No authentication or tracking expansion

Do not add user accounts, passwords, BYU sign-in, OAuth/OIDC, or other authentication in this release. Do not store IP addresses or introduce browser fingerprinting, advertising identifiers, or third-party tracking.

# Database Requirements

## DB-1 PostgreSQL

Use PostgreSQL.

Use the standard Node.js PostgreSQL driver:

```
pg
```

Do **not** use:

- Prisma
- Sequelize
- TypeORM
- Drizzle
- Knex
- any other ORM or database abstraction framework

The goal is to help students learn basic SQL and database connectivity with minimal abstraction.

---

## DB-2 Connection configuration

The application must obtain database configuration entirely from environment variables.

Required variables:

```
DATABASE_HOST
DATABASE_PORT
DATABASE_NAME
DATABASE_USER
DATABASE_PASSWORD
```

Do not hard-code any database settings.

---

## DB-3 No committed secrets

Do not commit:

- passwords
- connection strings
- credentials
- private keys
- populated `.env` files

---

## DB-4 Example configuration

Provide a committed:

```
.env.example
```

containing placeholder values.

Example:

```text
DATABASE_HOST=localhost
DATABASE_PORT=5432
DATABASE_NAME=cougarcalc
DATABASE_USER=your_username
DATABASE_PASSWORD=your_password
```

Also document the optional non-secret cookie setting:

```text
HISTORY_COOKIE_SECURE=false
```

Use `true` only when the browser reaches CougarCalc through HTTPS.

---

## DB-5 Database initialization

Provide a repeatable way to initialize the required database objects.

Acceptable approaches include:

- SQL initialization script
- lightweight migration script
- startup initialization

Choose the simplest solution appropriate for this project.

---

## DB-6 SQL safety

All SQL statements shall use parameterized queries (prepared statements).

Do not construct SQL statements by concatenating user input.

Example (conceptually):

```javascript
SELECT * FROM calculations WHERE id = $1
```

rather than:

```javascript
"SELECT * FROM calculations WHERE id = " + id
```

The goal is to model secure coding practices and prevent SQL injection vulnerabilities.

---

## DB-7 Release 2 history schema

Release 1 had no database. Provide one clean-install `001` migration containing the complete Release 2 calculation-history schema.

The migration shall:

- require every calculation row to have a valid hashed browser token;
- add the browser-scoped index that supports newest-first history lookup for one browser;
- avoid an unused global history-ordering index; and
- remain safe to run using the documented migration process.

Startup database-readiness verification shall require the non-null hash column, exact validated hash-format constraint, and browser-scoped index while retaining the type, identity, primary-key, and minimum-privilege checks.

# Architecture Requirements

## AR-1 Keep deployment simple

Continue using:

- Node.js
- Express

Do not introduce additional application frameworks unless absolutely necessary.

---

## AR-2 Separate configuration from code

Application behavior must not depend on environment-specific code changes.

Only environment variables should differ between deployments.

---

## AR-3 External database

Treat PostgreSQL as an external service.

Do not embed, launch, or manage PostgreSQL from the application.

---

## AR-4 Maintainability

Organize database code separately from route handlers where practical.

A small database access layer or module is encouraged if it improves readability.

Avoid scattering SQL statements throughout unrelated application files.

Keep the overall design straightforward and easy for undergraduate Information Systems students to understand.

- database connection logic
